The model (your decisions so far)
  • Toggle setting → one action "Toggle X". List → "Next X", "Previous X", and "Set X to <option>" for every option (both, per your answer). Slider → "Increase / Decrease / Reset X" by its step, only where the slider earns it (proposed per row). Commands are registered one by one.
  • Every action has an icon (flowbite-svelte-icons, already a dependency) and a per-profile Show on quick menu option. The quick-menu column below is the proposed DEFAULT; the user can change each.
  • Destructive commands are bindable and still open their confirmation dialog. All new actions ship unbound; only today's keys are defaults.
  • Every generated action announces the new value through the reader's overlay notification ("Brightness: 110%"), and a library toast outside the reader.
  • Hover-target actions (library cards, volume rows) act on the card under the pointer, like today's E/Delete/C.

Excluded by rule unless you flip them: setup-only settings (accounts, credentials, AnkiConnect URLs and field mapping, schedules' clock times, RAM tier, reset hour/day), anything needing typed input (rename, titles, page number), controls inside one-off modals (cover picker, volume editor fields), and transient prompts.

Decisions (owner, 2026-11-09)

  1. C and O: one action, "Spreads offset", default O. C is freed. (The cover toggle only overlapped the offset as a side effect.)
  2. P and Z: no split. Each stays ONE mode-aware cycle action (P = layout of the current mode, Z = zoom of the current mode). The per-setting "Set to" actions still exist, unbound.

  5. Text-box actions under the pointer: deferred past v1. "Copy whole page text" is in.
  6. Open settings: yes, with one shared open-state store.
  7. Every row left on "maybe" is bindable, unbound by default.
